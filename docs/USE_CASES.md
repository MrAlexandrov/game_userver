## Базовые сценарии

### UC-1: Создание викторины из YAML

**Актор**: Администратор

**Предусловия**: 
- Администратор имеет доступ к API
- YAML файл подготовлен и валиден

**Основной поток**:
1. Администратор отправляет POST запрос на `/packs/yaml` с YAML содержимым
2. Система парсит YAML
3. Система валидирует структуру (наличие title, questions, variants)
4. Система создает пак в БД
5. Система создает все вопросы в одной транзакции
6. Система создает все варианты ответов
7. Система возвращает ID созданного пака

**Постусловия**:
- Пак создан в БД
- Все вопросы и варианты созданы
- Администратор получил pack_id

**Альтернативные потоки**:
- 2a. YAML невалиден → возврат 400 Bad Request
- 4a. Ошибка БД → откат транзакции, возврат 500

**Пример**:
```bash
curl -X POST http://localhost:8080/packs/yaml \
  -H "Content-Type: text/plain" \
  -d '
title: География мира
questions:
  - text: Столица Франции?
    variants:
      - text: Париж
        is_correct: true
      - text: Лондон
      - text: Берлин
'
```

### UC-2: Проведение простой игры (2 игрока, 3 вопроса)

**Акторы**: Администратор, Игрок 1, Игрок 2

**Предусловия**:
- Пак вопросов создан (pack_id известен)
- Игроки готовы присоединиться

**Основной поток**:

**Фаза 1: Подготовка**
1. Администратор создает игровую сессию (POST `/games`)
2. Система создает сессию в состоянии `waiting`
3. Игрок 1 присоединяется (POST `/games/{id}/players`)
4. Система добавляет игрока, score = 0
5. Игрок 2 присоединяется
6. Система добавляет игрока, score = 0

**Фаза 2: Старт**
7. Администратор запускает игру (POST `/games/{id}/start`)
8. Система меняет состояние на `active`
9. Система уведомляет observers (логирование, уведомления)
10. Игроки получают уведомление о старте

**Фаза 3: Вопрос 1**
11. Игроки запрашивают состояние (GET `/games/{id}/state`)
12. Система возвращает вопрос #1 и варианты (без is_correct)
13. Игрок 1 отправляет ответ (POST `/games/{id}/answers`)
14. Система валидирует ответ, обновляет score если правильно
15. Игрок 2 отправляет ответ
16. Система валидирует ответ
17. **Все игроки ответили** → автоматический переход к вопросу #2

**Фаза 4: Вопросы 2-3**
18. Повторение шагов 11-17 для оставшихся вопросов

**Фаза 5: Завершение**
19. После последнего вопроса система меняет состояние на `finished`
20. Система уведомляет observers о завершении
21. Игроки получают финальные результаты (GET `/games/{id}/results`)

**Постусловия**:
- Игра завершена
- Все ответы сохранены
- Счета игроков подсчитаны
- Результаты доступны

**Временная диаграмма**:
```
t=0s    Создание сессии
t=5s    Игрок 1 присоединился
t=10s   Игрок 2 присоединился
t=15s   Старт игры
t=20s   Вопрос 1 - Игрок 1 ответил
t=25s   Вопрос 1 - Игрок 2 ответил → Переход к вопросу 2
t=30s   Вопрос 2 - Игрок 1 ответил
t=32s   Вопрос 2 - Игрок 2 ответил → Переход к вопросу 3
t=40s   Вопрос 3 - Игрок 1 ответил
t=45s   Вопрос 3 - Игрок 2 ответил → Игра завершена
t=46s   Получение результатов
```

### UC-3: Просмотр результатов игры

**Актор**: Любой пользователь (игрок, администратор, зритель)

**Предусловия**:
- Игра завершена (state = finished)
- game_id известен

**Основной поток**:
1. Пользователь запрашивает результаты (GET `/games/{id}/results`)
2. Система получает игровую сессию из БД
3. Система получает всех игроков с их счетами
4. Система сортирует игроков по убыванию счета
5. Система присваивает ранги (1, 2, 3, ...)
6. Система возвращает результаты

**Постусловия**:
- Пользователь видит финальную таблицу

**Пример ответа**:
```json
{
  "game_session": {
    "id": "...",
    "state": "finished",
    "current_question_index": 3
  },
  "players": [
    {
      "id": "...",
      "name": "Алексей",
      "score": 3,
      "rank": 1
    },
    {
      "id": "...",
      "name": "Мария",
      "score": 2,
      "rank": 2
    }
  ],
  "total_questions": 3
}
```

## Продвинутые сценарии

### UC-4: Игра с разными типами вопросов

**Актор**: Администратор, Игроки

**Предусловия**:
- Пак содержит вопросы разных типов:
  - `multiple_choice` - выбор варианта
  - `free_text` - свободный ответ

**Основной поток**:

**Вопрос 1: Multiple Choice**
1. Игрок получает вопрос с вариантами
2. Игрок выбирает вариант
3. Система использует `MultipleChoiceValidator`
4. Система проверяет `is_correct` выбранного варианта

**Вопрос 2: Free Text**
5. Игрок получает вопрос без вариантов
6. Игрок вводит текстовый ответ
7. Система использует `FreeTextValidator`
8. Система сравнивает с эталонными ответами в БД
9. Система учитывает регистр, пробелы, синонимы

**Пример запроса (free_text)**:
```json
POST /games/{id}/answers
{
  "player_id": "...",
  "text_answer": "Москва"
}
```

**Валидация free_text**:
```cpp
// В БД хранятся эталонные ответы:
// - "Москва"
// - "москва"
// - "Moscow"

bool FreeTextValidator::Validate(text_answer) {
    auto correct_answers = GetTextAnswersByQuestionId(question_id);
    
    for (auto& correct : correct_answers) {
        if (NormalizeText(text_answer) == NormalizeText(correct.text)) {
            return true;
        }
    }
    
    return false;
}
```

### UC-5: Турнирная игра (несколько раундов)

**Актор**: Администратор, Игроки

**Предусловия**:
- Несколько паков вопросов подготовлены
- Игроки готовы к длительной игре

**Основной поток**:

**Раунд 1**
1. Администратор создает игру с pack_1
2. Игроки присоединяются
3. Игра проводится (UC-2)
4. Результаты сохраняются

**Раунд 2**
5. Администратор создает новую игру с pack_2
6. Те же игроки присоединяются (новые player_id!)
7. Игра проводится
8. Результаты сохраняются

**Финал**
9. Внешняя система агрегирует результаты всех раундов
10. Подсчитывается общий счет
11. Определяется победитель турнира

**Примечание**: 
- Каждый раунд = отдельная game_session
- Агрегация результатов - вне текущей системы
- TODO: Добавить поддержку турниров на уровне БД

## Граничные случаи

### UC-7: Один игрок в игре

**Актор**: Одинокий игрок

**Предусловия**:
- Игра создана
- Только 1 игрок присоединился

**Основной поток**:
1. Игрок присоединяется
2. Администратор запускает игру
3. Игрок отвечает на вопрос
4. **Все игроки ответили** (1 из 1) → переход к следующему вопросу
5. Игра проходит нормально

**Постусловия**:
- Игра завершена
- Игрок получает результаты (rank = 1)

**Примечание**: Система корректно работает с 1 игроком

---

### UC-8: Много игроков (100+)

**Актор**: Администратор, 100 игроков

**Предусловия**:
- Пак вопросов создан
- 100 игроков готовы присоединиться

**Основной поток**:
1. Администратор создает игру
2. 100 игроков присоединяются (параллельно)
3. Администратор запускает игру
4. На каждый вопрос:
   - 100 игроков отправляют ответы (параллельно)
   - Система обрабатывает ответы
   - После 100-го ответа → переход к следующему вопросу

**Проблемы**:
- ⚠️ Race condition при проверке "все ответили"
- ⚠️ Высокая нагрузка на БД
- ⚠️ Долгое ожидание медленных игроков

**Решения**:
1. **Timeout на ответ**: 30 секунд, затем auto-submit
2. **Batch операции**: Группировка ответов
3. **Кэширование**: Состояние игры в памяти
4. **Sharding**: Разные игры на разных серверах

---

### UC-9: Игра без вопросов

**Актор**: Администратор

**Предусловия**:
- Пак создан, но вопросов нет

**Основной поток**:
1. Администратор создает игру с пустым паком
2. Игроки присоединяются
3. Администратор запускает игру
4. Система пытается получить текущий вопрос
5. **Вопросов нет** → возврат 404 Not Found

**Альтернативный поток**:
- 1a. Система проверяет количество вопросов при создании игры
- 1b. Если вопросов нет → возврат 400 Bad Request

**Рекомендация**: Добавить валидацию при создании игры

## Сценарии ошибок

### UC-10: Игрок отключился во время игры

**Актор**: Игрок 1 (отключился), Игрок 2

**Предусловия**:
- Игра активна
- 2 игрока в игре
- Игрок 1 отключился

**Текущее поведение**:
1. Игрок 2 отвечает на вопрос
2. Система ждет ответа Игрока 1
3. **Deadlock** - игра не может продолжиться

**Проблема**: Нет механизма timeout

**Решение 1: Timeout**
```
1. Игрок 2 отвечает
2. Система запускает таймер (30 секунд)
3. Если Игрок 1 не ответил за 30 секунд:
   - Система автоматически отправляет пустой ответ (неправильный)
   - Переход к следующему вопросу
```

**Решение 2: Skip**
```
1. Игрок 2 может нажать "Skip waiting"
2. Система помечает Игрока 1 как AFK
3. Игра продолжается без него
```

**Решение 3: Kick (для администратора)**
```
POST /games/{id}/kick
{
  "player_id": "..."
}
```

### UC-11: Попытка ответить дважды

**Актор**: Читер

**Предусловия**:
- Игра активна
- Игрок уже ответил на текущий вопрос

**Основной поток**:
1. Игрок отправляет первый ответ → Success
2. Игрок пытается отправить второй ответ
3. Система проверяет историю ответов
4. **Игрок уже ответил** → возврат 400 Bad Request

**Проверка**:
```sql
SELECT COUNT(*) 
FROM quiz.player_answers 
WHERE player_id = $1 AND question_id = $2
```

Если count > 0 → ошибка

**Основной поток**:
1. Игрок пытается отправить ответ

### UC-13: База данных недоступна

**Актор**: Любой пользователь

**Предусловия**:
- PostgreSQL недоступен (сеть, перезагрузка, etc.)

**Основной поток**:
1. Пользователь отправляет запрос
2. Handler вызывает GameService
3. GameService вызывает Storage
4. Storage пытается подключиться к БД
5. **Connection timeout** → Exception
6. GameService ловит exception
7. Handler ловит exception
8. Логирование ошибки
9. Возврат 500 Internal Server Error

**Обработка**:
```cpp
try {
    auto result = NStorage::SubmitPlayerAnswer(...);
} catch (const userver::storages::postgres::Error& e) {
    LOG_ERROR() << "Database error: " << e.what();
    throw std::runtime_error("Failed to submit answer");
}
```

- Fallback на read replica

## Интеграционные сценарии

### UC-18: Интеграция с Telegram Bot

**Актор**: Telegram Bot, Игроки в Telegram

**Предусловия**:
- Telegram Bot развернут
- Bot имеет доступ к API

**Основной поток**:

**В Telegram**:
1. Пользователь отправляет `/start` боту
2. Бот показывает список доступных паков
3. Пользователь выбирает пак
4. Бот создает игру через API (POST `/games`)
5. Бот отправляет ссылку для присоединения

**Присоединение игроков**:
6. Другие пользователи нажимают "Join"
7. Бот добавляет их через API (POST `/games/{id}/players`)
8. Бот показывает список участников

**Игра**:
9. Создатель нажимает "Start"
10. Бот запускает игру через API (POST `/games/{id}/start`)
11. Бот отправляет вопрос всем игрокам
12. Игроки отвечают через inline кнопки
13. Бот отправляет ответы через API (POST `/games/{id}/answers`)
14. Бот показывает результаты после каждого вопроса

**Завершение**:
15. Бот получает финальные результаты (GET `/games/{id}/results`)
16. Бот отправляет красивую таблицу с результатами

**Преимущества интеграции**:
- Удобный UI для пользователей
- Уведомления через Telegram
- Групповые игры в чатах
